Parcours d'affichage des offres

Gesta est un monorepo TypeScript composé d'un frontend React/Vite, d'une API Express et d'une base SQLite. Cette page suit une requête d'offres depuis le composant React jusqu'aux tables SQLite, puis son retour vers l'interface.

Vue d'ensemble

1Interface React

App.tsx vérifie la session et rend OffersPage pour les profils autorisés. La page appelle useOffers, qui lance le chargement et transmet les résultats à OfferTable.

2Appel HTTP

offers.service.ts appelle /api/offers avec le jeton dans Authorization. Le proxy Vite retire /api avant d'envoyer la requête à l'API.

3API Express

Le middleware authentifie l'utilisateur, puis authorize vérifie canListOffers. Le contrôleur appelle le service métier.

4Règle métier

offers.service.ts convertit le profil en filtre : toutes les offres pour un administrateur, les publiées pour un étudiant, celles déposées par le contact pour un déposant.

5SQL et SQLite

Le repository exécute la requête préparée sur offers, avec des jointures vers companies, academic_years et periods, puis trie par année et date de création.

6Retour et affichage

Le mapper transforme la ligne SQL en modèle puis en DTO public. Le type guard frontend valide le JSON; le tableau affiche titre, entreprise, année, période et statut.

Détail du parcours

1. Rendu et chargement frontend

frontend/src/App.tsx ne crée la route /offres que si canListOffers l'autorise pour l'affichage. Cette condition améliore l'interface, mais la sécurité réelle reste côté backend.

frontend/src/pages/OffersPage.tsx utilise frontend/src/hooks/useOffers.ts. Le hook gère le chargement, l'annulation via AbortController, les erreurs et le retour à la connexion en cas de réponse HTTP 401.

2. Contrat HTTP et validation

frontend/src/services/offers.service.ts appelle GET /api/offers. readJson vérifie le statut HTTP et isOfferList valide chaque élément avant de le retourner.

Le DTO contient uniquement id, title, companyShortName, academicYear, period et status.

3. Authentification et autorisation

backend/src/controllers/offers.controller.ts branche authorize(canListOffers). L'utilisateur courant est fourni par le middleware d'authentification, qui relit son identité, ses rôles et ses entreprises depuis SQLite.

Un contact qui n'a pas le rôle DEPOSITOR obtient 403; un utilisateur non authentifié obtient 401.

4. Filtrage, mapping et affichage

backend/src/services/offers.service.ts produit un OfferFilter. Le repository renvoie des OfferDbo; offer.mapper.ts les convertit en modèle métier puis en OfferDto.

frontend/src/components/OfferTable.tsx rend la propriété period avec les libellés de frontend/src/utils/labels.ts.

Requête SQL actuelle

SELECT o.id, o.title, o.description, o.status,
       o.company_id, c.short_name AS company_short_name,
       o.depositor_contact_id,
       ay.label AS academic_year_label, p.code AS period_code,
       o.created_at, o.updated_at
FROM offers o
JOIN companies c ON c.id = o.company_id
JOIN academic_years ay ON ay.id = o.academic_year_id
JOIN periods p ON p.id = o.period_id
WHERE (@status IS NULL OR o.status = @status)
  AND (@depositorContactId IS NULL
       OR o.depositor_contact_id = @depositorContactId)
ORDER BY ay.start_date DESC, o.created_at DESC

Ajout d'un filtre par période

La période existe déjà dans le modèle et dans la base (P1, P2, OTHER). Il s'agit donc d'ajouter un paramètre de recherche et de le propager jusqu'au repository, sans migration de schéma.
