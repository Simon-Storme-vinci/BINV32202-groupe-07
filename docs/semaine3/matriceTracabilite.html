Matrice de traçabilité des tests

Cette matrice confronte les exigences EF-32 et EF-33 du cahier des charges aux tests existants. La couverture est jugée d’après les assertions qui établissent le résultat attendu, pas seulement d’après l’appel d’une route.

Source des exigences : cahier des charges, § 7.4. Les tests API sont dans applications.test.ts ; les tests d’interface concernés sont ApplicationsPage.test.tsx et OffersPage.test.tsx.

Couvert : cas effectivement vérifié Partiel : assertion incomplète ou cas confondu Absent : aucun test probant relevé

EF-32 — Candidater et retirer sa candidature

Cas normaux, refus et limites de la création et du retrait d’une candidature.
Exigence Cas à vérifier Résultat attendu Test existant (fichier et nom) Assertions utiles Couverture
EF-32 Créer une candidature à une offre publiée, avec un message. La candidature est créée ; son statut initial est « En cours » et le message est conservé. API — « crée une candidature puis refuse le doublon actif » first.status === 201, first.body.status === "IN_PROGRESS" et first.body.message === "Je suis motivée". L’offre Fleet App du seed est publiée. Couvert
EF-32 Créer une candidature sans message (message facultatif). La création réussit et le message peut être absent ou nul. API — « retire logiquement une candidature et autorise une nouvelle candidature » Le test poste sans propriété message et vérifie created.status === 201 ainsi que created.body.message === null. Couvert
EF-32 Accéder au formulaire de candidature depuis une offre. L’étudiant peut ouvrir le formulaire et saisir un message facultatif avant confirmation. Interface — « ouvre la modale de candidature depuis une offre » Le test vérifie la boîte de dialogue, le champ Message (facultatif) et le bouton Confirmer. Il ne vérifie pas l’envoi de la candidature ni la réponse de l’API. Partiel
EF-32 Refuser une candidature à une offre non publiée. Aucune candidature n’est créée ; l’API refuse l’offre. API — « refuse une candidature à une offre non publiée de l'année courante » response.status === 404, response.body.error.code === "NOT_FOUND" et une vérification que la candidature n’apparaît pas dans la liste. L’offre Client Portal est SUBMITTED et de l’année courante : données du seed. Couvert
EF-32 Retirer sa candidature tant qu’elle n’a pas été traitée. Le retrait réussit ; la candidature reste historisée avec le statut « Retirée ». API — « retire logiquement une candidature et autorise une nouvelle candidature » Après withdrawn.status === 204, GET vérifie que l’identifiant initial est encore listé avec status === "WITHDRAWN" ; une nouvelle candidature reçoit ensuite 201 et un nouvel ID. Couvert
EF-32 Refuser le retrait d’une candidature déjà traitée. Le retrait est refusé avec un conflit indiquant que la candidature a déjà été traitée. API — « refuse de retirer une candidature déjà traitée » response.status === 409 et response.body.error.code === "APPLICATION_PROCESSED". L’identifiant 3 correspond à une candidature SELECTED du seed. Couvert
EF-32 Depuis l’interface, confirmer le retrait d’une candidature. Après confirmation, l’interface envoie une requête DELETE sur la candidature choisie. Interface — « retire une candidature après confirmation » Le test clique sur Retirer et vérifie que le fetch vise /api/applications/1 avec la méthode DELETE. La réponse simulée 204 n’est pas suivie d’une assertion sur l’état affiché ou le statut persisté. Partiel
EF-32 Réserver création et retrait aux étudiants. Un utilisateur non étudiant ne peut ni candidater ni retirer une candidature. API — « refuse l'accès aux candidatures pour un utilisateur non étudiant » Pour un administrateur, GET, POST et DELETE renvoient chacun 403 avec le code FORBIDDEN. Couvert
EF-32 Un étudiant ne peut pas retirer la candidature d’un autre. Le retrait de la candidature étrangère est refusé et celle-ci reste active pour son propriétaire. API — « refuse à un étudiant de retirer la candidature d'un autre étudiant » La requête étrangère reçoit 404 / NOT_FOUND ; une lecture sous l’identité du propriétaire retrouve l’ID avec IN_PROGRESS. Couvert

EF-33 — Consulter ses candidatures et leur statut

Isolation des données de l’étudiant et vérification des statuts affichés.
Exigence Cas à vérifier Résultat attendu Test existant (fichier et nom) Assertions utiles Couverture
EF-33 Un étudiant ne voit pas les candidatures d’un autre étudiant. La réponse ne contient que les candidatures du compte connecté. API — « liste uniquement les candidatures de l'étudiant connecté » La requête est faite comme Lucas ; response.body a une longueur de 1 et contient l’offre Fleet App avec le statut IN_PROGRESS. Le seed contient aussi, sur cette même offre, une candidature d’Inès : la taille vérifiée exclut donc cette candidature étrangère. Voir les candidatures du seed. Couvert
EF-33 Afficher le statut « En cours ». L’étudiant voit un libellé compréhensible pour le statut en cours. Interface — « affiche les candidatures et leurs statuts » findByText("Application React") et getByText("En cours") sont vérifiés sur la page. L’API vérifie aussi IN_PROGRESS dans la réponse de liste. Couvert
EF-33 Afficher le statut « Retirée ». Une candidature retirée reste visible avec le libellé « Retirée ». Interface — « affiche les candidatures et leurs statuts » getByText("Retirée") est vérifié sur une donnée simulée. L’API vérifie désormais le statut WITHDRAWN pour Inès, mais les tests ne valident pas l’intégration réelle entre cette réponse et cet affichage. Partiel
EF-33 Afficher les statuts « Retenue » et « Non retenue ». Les deux statuts sont retournés par l’API et affichés avec leur libellé. API — « liste les statuts de candidature de l'étudiant connecté » ; aucun test d’affichage de ces deux statuts n’a été relevé. Les réponses API de Mateusz et Léa sont vérifiées avec SELECTED et REJECTED. Aucun test d’interface ne vérifie encore les libellés « Retenue » et « Non retenue » : seed.test.ts. Le mapping existe dans labels.ts, mais il n’a pas été vérifié ici par un test de rendu ou une vérification navigateur. Partiel

Comportements testés hors EF-32 / EF-33

Ces tests sont utiles, mais vérifient des règles ou détails d’implémentation qui ne sont pas explicitement formulés dans EF-32 ou EF-33. Ils ne sont donc pas comptés comme couverture de ces exigences.

  • Le doublon de candidature active est refusé avec 409 et APPLICATION_EXISTS : règle de non-duplication.
  • Un message de 301 caractères est refusé avec 400 : limite de validation documentée par l’API, mais absente du texte EF-32.
  • La page signale une session expirée en appelant onUnauthorized après une réponse 401 : comportement d’authentification, hors EF-32 / EF-33.

Conclusion : les tests API couvrent maintenant le refus isolé d’une offre non publiée, la persistance du retrait, les statuts en liste, ainsi que les droits d’accès et la propriété des candidatures. La principale lacune restante concerne l’affichage, dans l’interface, des statuts « Retenue » et « Non retenue » ; l’intégration réelle des statuts API avec les libellés UI n’est pas testée de bout en bout. Aucune vérification manuelle navigateur n’a été effectuée ; une vérification complémentaire consisterait à ouvrir la page des candidatures avec les comptes Mateusz (retenue) et Léa (non retenue).
